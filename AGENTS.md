# Работа с репозиторием

## Область

main содержит инфраструктуру и документацию каркаса, а не реализацию мода.
Проверки каркаса находятся в `tests/repository.test.mjs`.
Код фичи, его тесты, инструкции и записи CHANGELOG добавляй в отдельной
тематической ветке от main. Не описывай будущие функции как уже реализованные.

## Процесс

1. Проверь ветку, status и diff; сохрани посторонние изменения.
   Меняй main только по прямому указанию пользователя.
2. Для нетривиальной логики подтверди регрессионный тест RED → GREEN.
   Сохраняй минимальный размер и существующую структуру изменений.
3. Выполни `npm run check` и `git diff --check`.
   Дополнительные проверки новых компонентов документируй вместе с ними.
4. В отчёте отделяй выполненные проверки от пропущенных.
   Локальный запуск не доказывает успешный GitHub CI.

Новые зависимости требуют обоснования. При изменении внешней интеграции сначала
проверь её действующий контракт; тестовая замена API не доказывает работу хоста.

## Границы безопасности

- Секреты, пользовательскую конфигурацию, логи и приватные снимки держи вне git.
- Установка кода, изменение внешней системы и работа с пользовательскими
  процессами требуют отдельного разрешения.
- Push, теги, релизы, видимость и rulesets GitHub выполняй только по запросу.
  Публикуй лишь согласованные ветки; `backup/*` сохраняй локально.
- Историю не переписывай без отдельного согласования. Рабочий email авторов
  разрешён владельцем; самостоятельно его не заменяй.
- Лицензии, notices и происхождение стороннего кода сохраняй вместе с этим кодом.

Сообщение коммита: `(тип): <действие по-русски глаголом в прошедшем времени>`.
Например: `(chore): добавил проверку конфигурации CI`.

Процесс PR и публикации — в [CONTRIBUTING.md](CONTRIBUTING.md).
Уязвимости — по [SECURITY.md](SECURITY.md), а не в публичном issue.
